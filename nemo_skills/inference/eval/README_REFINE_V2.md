# Refine V2: Structured Hypothesis Feedback

This document describes refine v2, an eval-side variant that replaces the basic v1 handoff with a structured debugging summary and an explicit hypothesis-revision instruction.

## One-line Summary

Refine v2 still runs a clean-repo multi-attempt SWE-agent chain. The difference is the attempt-to-attempt seed. Instead of only passing the previous patch plus raw verifier log tail, v2 passes structured verifier evidence:

```text
previous patch metadata
changed files
FAIL_TO_PASS failures
PASS_TO_PASS regressions
key verifier failure snippet
raw verifier output tail
artifact paths
previous patch diff
explicit hypothesis revision questions
```

The intent is to make attempt 1 behave less like a blind retry and more like a debugging pass.

## Current Eval Config

Typical eval config:

```text
agent_framework=swe_agent_refine
refine_strategy=structured_hypothesis
max_attempts=2
agent_max_turns=200
carry_over_token_budget=40000
refine_verify_feedback_chars=8000
refine_failure_snippet_chars=4000
refine_max_changed_files_in_seed=30
refine_max_tests_in_seed=30
refine_write_full_artifacts=True
```

## Attempt Flow

```text
Original SWE-bench problem_statement
  |
  v
Attempt 0: SWE-agent on clean repo
  |
  v
Extract model_patch and trajectory
  |
  v
Run SWE-bench verifier
  |-- resolved=True  -> stop, chain success
  |
  |-- unresolved
       |
       v
Build structured feedback:
  - patch metadata
  - verifier status
  - failure type
  - failed tests
  - key failure snippet
  - raw verifier tail
  - artifact paths
       |
       v
Attempt 1: SWE-agent on clean repo with structured seed appended
       |
       v
Run SWE-bench verifier again
       |-- resolved=True  -> chain success
       |-- unresolved     -> chain failure
```

As in v1, workspace state is not preserved across attempts. Only text and artifact paths are passed forward.

## V2 Seed

The v2 seed is built by `_build_refine_seed_v2`. Conceptually:

````text
---
Your previous automated attempt did NOT resolve the issue.

You are starting again from a clean repository. You do not inherit the previous workspace state.
Use the previous attempt only as debugging evidence.

Previous attempt structured summary:
- Attempt: 0
- Patch existed: true
- Patch successfully applied by verifier: true
- Failure type: target_tests_still_failing
- Changed files: 2
- Added lines: 18
- Removed lines: 4

Files changed by the previous patch:
- path/to/file.py

Failing FAIL_TO_PASS tests from the verifier:
- tests/test_bug.py::test_expected_fix

Regressed PASS_TO_PASS tests from the verifier:
- tests/test_existing_behavior.py::test_existing_behavior

Key verifier failure snippet:
```text
<extracted traceback/assertion/error-focused snippet>
```

Raw verifier output tail:
```text
<last refine_verify_feedback_chars chars of test_output.log>
```

Full artifacts, if you need to inspect them:
- Previous patch: /workspace/.../previous.patch
- Full verifier log: /workspace/.../test_output.log
- Structured feedback JSON: /workspace/.../feedback.json

Previous patch:
```diff
<previous model_patch, middle-truncated by carry_over_token_budget>
```

Before editing, revise your debugging hypothesis:
1. What was the previous patch likely trying to fix?
2. What evidence shows it was incomplete or wrong?
3. Which parts of the previous patch should be kept, changed, or ignored?
4. Which files/functions should be inspected first?

Then produce a minimal correct patch. Avoid repeating the same failed approach unless the verifier evidence supports it.
````

## Key Verifier Failure Snippet

The `Key verifier failure snippet` is not generated by another model. It is extracted from the SWE-bench verifier log.

Extraction rule:

| Case | Behavior |
|---|---|
| Log contains `Traceback (most recent call last)` | Take the last traceback and truncate to `refine_failure_snippet_chars` |
| No traceback | Find lines containing assertion, failed, error, syntax/import errors, timeout, or pytest `E` lines |
| Matching lines found | Include a small window around each interesting line |
| Nothing found | Fall back to the verifier output |

Default:

```text
refine_failure_snippet_chars=4000
```

This snippet is meant to front-load the highest-signal failure evidence before the raw log tail.

## Structured Feedback Artifacts

When `refine_write_full_artifacts=True`, v2 writes per-attempt feedback artifacts:

```text
refine_feedback/<instance_id>_a0/
  previous.patch
  feedback.json
  feedback.md
```

The `feedback.json` contains:

```json
{
  "attempt": 0,
  "strategy": "structured_hypothesis",
  "patch": {
    "changed_files": [],
    "num_changed_files": 0,
    "num_added_lines": 0,
    "num_removed_lines": 0,
    "num_hunks": 0,
    "num_chars": 0,
    "approx_tokens": 0
  },
  "verifier": {
    "resolved": false,
    "failure_type": "no_patch",
    "fail_to_pass_failed": [],
    "pass_to_pass_failed": [],
    "unknown_failed_tests": []
  },
  "snippets": {
    "key_failure_snippet": "...",
    "raw_verify_tail": "..."
  },
  "artifacts": {}
}
```

## Failure Types

V2 uses the same failure classifier as v1:

| Failure type | Meaning |
|---|---|
| `resolved` | Attempt passed SWE-bench verification |
| `no_patch` | Agent did not produce a usable model patch |
| `patch_apply_failed` | Patch exists but verifier could not apply it |
| `eval_error` | Verifier execution failed |
| `timeout` | Verifier log indicates timeout |
| `syntax_or_import_error` | Syntax/import/module error in verifier output |
| `target_tests_still_failing` | FAIL_TO_PASS tests still fail |
| `regression_introduced` | PASS_TO_PASS tests fail |
| `mixed_failure` | Both target failures and regressions |
| `unknown_tests_failing` | Failed tests were detected but not matched to known lists |
| `unknown_unresolved` | Unresolved without a more specific category |

Run:

Breakdown:

| Metric | Value |
|---|---:|
| Attempt 0 resolved | 35 |
| Attempt 1 rescued | 3 |
| Final resolved | 38 |
| Final unresolved | 62 |
| Refine attempted | 65 |
| Rescue rate among refined samples | 3/65 = 4.6% |

Failure type transition summary:

| Field | Distribution |
|---|---|
| `attempt0_failure_type` | resolved 35, target_tests_still_failing 32, no_patch 26, mixed_failure 6, regression_introduced 1 |
| `final_failure_type` | resolved 38, target_tests_still_failing 32, no_patch 24, mixed_failure 6 |
| `rescued_from_failure_type` | no_patch 3 |

Compared with v1 on the same eval100:

| Metric | V1 basic | V2 structured |
|---|---:|---:|
| Final resolved | 45 | 38 |
| Attempt 0 resolved | 33 | 35 |
| Attempt 1 rescued | 12 | 3 |
| Refine attempted | 67 | 65 |

Interpretation: v2 did not fail at attempt 0. The loss came from much weaker attempt 1 rescue. The structured seed may be too long or too prescriptive for the current 4B model.

Caveat: this 64k run hit context length validation errors. V2 adds extra structured text on top of the previous patch and raw verifier tail, so it is more sensitive to prompt length.

## Porting V2 to Multi-turn Training

V2 is useful if training should teach an explicit debugging behavior:

```text
observe previous failure
summarize evidence
revise hypothesis
decide what to keep/change/ignore
produce new patch
```

Recommended training-side attempt 1 observation:

````text
Original problem statement

Previous attempt summary:
- Patch existed
- Patch applied
- Failure type
- Changed files
- Patch size

Failing target tests:
<FAIL_TO_PASS failed tests>

Regressed tests:
<PASS_TO_PASS failed tests>

Key verifier failure snippet:
<traceback/assertion-focused snippet>

Previous patch:
<diff>

Before editing:
1. State what the previous patch tried to fix.
2. State why it failed.
3. State what to keep/change/ignore.
4. Inspect the most relevant files.
````

For training, consider making the hypothesis revision an explicit assistant turn before tool use. That gives the model a learnable intermediate skill and lets you log whether it repeats the same failed approach.

## Training Metrics to Add

Use all v1 metrics, plus v2-specific structured-observation metrics.

Structured seed metrics:

| Metric | Meaning |
|---|---|
| `structured_seed_chars` | Full v2 carry-over seed length |
| `structured_seed_tokens_est` | Approx token estimate |
| `key_failure_snippet_chars` | Snippet length |
| `raw_verify_tail_chars` | Raw verifier tail length |
| `num_failed_tests_in_seed` | Failed tests included in prompt |
| `num_changed_files_in_seed` | Changed files included in prompt |
| `has_artifact_paths` | Whether full log/patch paths were provided |

Hypothesis metrics:

| Metric | Meaning |
|---|---|
| `hypothesis_turn_present` | Model produced a debugging hypothesis before edits |
| `hypothesis_mentions_failure_type` | Mentions target failure/regression/no patch/etc. |
| `hypothesis_mentions_failed_test` | Mentions concrete failed test name |
| `hypothesis_mentions_changed_file` | Mentions previous changed file |
| `hypothesis_keep_change_ignore_count` | Whether it explicitly decides what to keep/change/ignore |

Repair behavior metrics:

| Metric | Meaning |
|---|---|
| `changed_file_overlap_with_previous` | Revisited previous files |
| `new_changed_files_count` | Opened/edited new files after failure |
| `failed_test_overlap_with_previous` | Same tests still fail |
| `failure_type_transition` | Attempt k failure -> attempt k+1 failure |
| `target_failure_delta` | FAIL_TO_PASS failures reduced or increased |
| `regression_delta` | PASS_TO_PASS failures reduced or increased |

Context-risk metrics:

| Metric | Meaning |
|---|---|
| `context_length_error` | Server rejected prompt as too long |
| `seed_truncated` | Any seed component was truncated |
| `patch_truncated` | Previous diff was truncated |
| `verify_tail_truncated` | Verifier output tail was truncated |
| `snippet_equals_raw_tail` | Whether key snippet added no extra compression |

Outcome metrics:

| Metric | Meaning |
|---|---|
| `chain_resolved` | Any attempt solved |
| `resolved_at_attempt` | First successful attempt |
| `refine_rescued` | Later attempt fixed attempt0 failure |
| `rescued_from_failure_type` | Which failure type was rescued |
| `num_repeat_failure_attempts` | Attempts that repeated failed tests |

For reward shaping, avoid rewarding verbose summaries directly. Prefer outcome-tied deltas:

```text
reward =
  final_resolved_bonus
  + target_failure_reduction_bonus
  - regression_penalty
  - repeat_failure_penalty
  - context_overflow_penalty
```

V2 should be considered successful only if the structured observation improves rescue rate or reduces repeated failures relative to v1.
